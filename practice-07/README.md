## Цель и результат

Цель: собрать интерфейс списка задач из компонентов React. Состояние хранится в одном
месте, данные меняются только новыми объектами, а всё, что можно вычислить, считается
при рендере.

Результат: задачи можно создавать, править, переключать и удалять с подтверждением.
Список фильтруется по четырём полям и сортируется. Статистика всегда считается по
всему набору. Данные живут в памяти страницы. Ни `localStorage`, ни сервера, ни
`useEffect` в работе нет.

Кто владеет состоянием:

| Состояние | Владелец | Почему там |
|---|---|---|
| `tasks`, `filters`, `editingId`, `sort`, `notice` | `App` | нужны нескольким компонентам |
| черновик и ошибки формы | `TaskForm` | никому, кроме формы, не нужны до отправки |
| `visibleTasks`, `stats`, `editingTask` | никто, вычисляются при рендере | иначе две копии одних данных разойдутся |

### Неизменяемые обновления, ключи, сброс формы

- Все изменения идут через функции домена. Они возвращают новый массив, где новый объект
  есть только у изменённой задачи, а остальные ссылки те же. Это проверяет собственный
  тест О3.
- Обновления функциональные: `setTasks(previous => …)`. Новый `id` считается внутри
  обновления как `nextTaskId(previous)`, то есть максимум плюс один. От длины массива он
  не зависит, поэтому после удаления id не повторяются.
- У карточки `key = task.id`. Индекс не годится: после фильтра или сортировки React
  связал бы состояние строки с чужой задачей.
- Ключ формы: `edit-<id>` при правке, `create` при создании. Смена ключа монтирует
  новую форму, и черновик заново берётся из `initialTask`. Так переход «правка A →
  правка B» показывает B (сценарий 6), а после удаления редактируемой задачи
  открывается пустая форма создания (сценарий 10).
- `window.confirm` вызывается до `setTasks`. Функция обновления остаётся чистой и не
  спрашивает дважды, хотя `StrictMode` в dev вызывает её два раза.
- `onSave` возвращает `false`, если редактируемой задачи уже нет. Тогда форма
  сохраняет черновик и показывает сообщение в `role="alert"`.

### Доступность

- Сообщения об ошибках связаны с полями через `aria-describedby`, а у неверного поля
  стоит `aria-invalid`.
- Итог действия попадает в `role="status"`.
- У кнопок карточки `aria-label` с названием задачи.
- Фокус видно по рамке 3 px.
- Форма с `noValidate` и без `maxLength`: так ошибку на 101 символ можно увидеть,
  браузер не обрезает ввод.

## Расширение: порядок списка

`sortTasks(tasks, sort)` возвращает новый массив (`toSorted`). Названия сравнивает
`Intl.Collator('ru')`, приоритет идёт от высокого к низкому. При одинаковом ключе
сохраняется исходный порядок.

Порядок хранится в `App` рядом с фильтрами и применяется к готовой выборке:
`sortTasks(selectTasks(tasks, filters), sort)`. Статистику он не меняет, сброс
фильтров его не трогает.

## Ответы на контрольные вопросы

1. **JSX и строка HTML.** JSX — это выражения JavaScript, которые собираются в вызовы
   `jsx()` и дают объекты-описания элементов. Значения в фигурных скобках React
   вставляет как текст, поэтому `<img …>` в названии остаётся текстом (сценарий 14).
   Строку HTML пришлось бы разбирать через `innerHTML`, и разметка бы выполнилась.
   В JSX свои имена атрибутов (`className`, `htmlFor`), и обработчики передаются
   функциями.
2. **Props и состояние.** Props приходят от родителя, и компонент их только читает.
   Состояние принадлежит компоненту, меняется через `set…`, и каждая смена вызывает
   рендер. Например, `tasks` — состояние `App`, а для `TaskList` это props.
3. **Обычная переменная вместо `useState`.** Между рендерами она не сохраняется: функция
   компонента вызывается заново, и значение начинается сначала. Присваивание не
   просит React перерисовать экран.
4. **Функциональная форма обновления.** Она нужна, когда новое значение зависит от
   прежнего: `setTasks(previous => toggleTask(previous, id))`. React отдаёт последнее
   состояние с учётом обновлений из очереди, а значение из замыкания могло устареть.
5. **Мутация объекта в поверхностной копии.** Копия массива ссылается на те же объекты.
   Если поменять объект задачи, изменится и прежнее состояние. Сравнение ссылок
   перестанет видеть разницу, а `StrictMode` с двойным вызовом получит уже
   изменённые данные. Поэтому меняется только новый объект задачи.
6. **Стабильный `key`.** По ключу React понимает, какая строка какой задаче
   соответствует. Индекс меняется при фильтре, сортировке и удалении, и DOM вместе с
   состоянием строки перешёл бы к другой задаче. `task.id` от положения в списке не
   зависит.
7. **Выборка и статистика без своего состояния.** Обе однозначно вычисляются из `tasks`
   и `filters`. Отдельная копия требовала бы синхронизации на каждом изменении и при
   первой же ошибке разошлась бы с данными. Вычисление на 12–100 задачах ничего не стоит.
8. **Как дочерний компонент сообщает о действии.** Он вызывает функцию из props:
   `onToggle(task.id)`, `onChange(nextFilters)`, `onSave(value)`. Решает и меняет
   состояние родитель.
9. **Управляемое поле.** Его значение задаёт `value` из состояния, а каждое изменение
   проходит через `onChange` и `set…`. Источник правды — состояние, а не DOM.
10. **`categoryId` из `select`.** `value` у `select` всегда строка, а в данных
    `categoryId` — число. `validateTaskDraft` переводит строку в число через
    `toCategoryId` (только цифры) и проверяет, что такая категория есть. Иначе
    сравнение `'2' === 2` в фильтре и при поиске названия категории не сработает.
11. **Смена ключа формы.** React размонтирует старый экземпляр и монтирует новый. Всё
    локальное состояние, то есть черновик и ошибки, создаётся заново из начального
    значения `useState(() => createDraft(initialTask))`.
12. **`confirm` вне функции обновления.** Функция обновления должна быть чистой: React
    может вызвать её повторно (в `StrictMode` вызывает дважды) или отложить.
    Модальный вопрос внутри неё был бы побочным эффектом, и пользователя спросили бы
    два раза.
13. **Нет задач или нет совпадений.** `TaskList` получает и выборку, и `totalCount`.
    При `totalCount === 0` выводится «Задач пока нет», при пустой выборке и непустом
    наборе — «Под выбранные фильтры ничего не подходит» (сценарии 12 и 15).
14. **Что проверяет `npm test`.** Только чистый домен: проверку черновика, выборку,
    статистику, неизменяемые операции, а также мои тесты сортировки, id и варианта.
    Рендер, обработчики, ключи формы, доступность, `confirm` и консоль он не
    проверяет. Это закрывает ручной протокол.
15. **Что изменится для API в ПР8.**
    - Исходные `tasks` и `categories` будут загружаться с сервера, и появятся состояния
      «загрузка», «ошибка», «готово».
    - Обработчики станут асинхронными: создание, правка и удаление пойдут запросами,
      `id` будет выдавать сервер, поэтому `nextTaskId` уйдёт.
    - `onSave` будет возвращать промис, и форма будет ждать ответа.
    - Фильтры можно будет передавать серверу.
    - Компоненты отображения и функции проверки останутся почти без изменений.

## Вывод

Интерфейс разделён на пять компонентов, состояние хранится только в `App`, и все
изменения идут через чистые функции домена. Благодаря этому тесты проверяют логику без
браузера, а компоненты только показывают данные и передают события наверх.

Самые тонкие места — ключ формы, функциональные обновления и `confirm` вне функции
обновления. Именно на них ломаются сценарии 6, 10 и 15, и все три проходят. Вариант 1
показывает, зачем статистика и выборка считаются отдельно: задача исчезает из списка,
а счётчик «Выполнено» растёт.
