## Цель и результат

Цель: заменить `localStorage` из ПР4 настоящим HTTP API. Интерфейс читает и меняет
задачи только запросами, показывает состояния загрузки и не даёт устаревшему ответу
затереть свежий.

Результат: работают создание, редактирование, смена статуса, удаление и сброс. После
каждой мутации список запрашивается заново. Остановленный API даёт состояние `error` и
кнопку повтора, а быстрые фильтры не смешивают ответы.

## Как устроено

Слои зависят только сверху вниз. Контроллер не знает про DOM, представление не знает про
HTTP.

```
dom-app.js ──события──▶ app-controller.js ──▶ task-api.js ──▶ api-client.js ──▶ fetch
     ▲                        │                    │
     └──── view.set*() ◀──────┘           проверка схемы ответа
```

| Модуль | Ответственность |
|---|---|
| `src/api-client.js` | URL и query, методы GET/POST/PATCH/DELETE, JSON-тело, тайм-аут и отмена, вид ошибки (`http`, `network`, `timeout`, `aborted`, `invalid-response`) |
| `src/task-api.js` | операции над задачами, проверка фильтров до запроса, проверка схемы каждого ответа |
| `src/form-validation.js` | чистая функция: черновик формы превращается в `{ valid, value, errors }` |
| `src/task-view.js` | карточка `li.task-card` и перерисовка списка через `replaceChildren` |
| `src/app-controller.js` | состояние, загрузка с отменой, общая схема мутации |
| `src/debounce.js` | расширение: откладывает вызов до паузы ввода |
| `src/dom-app.js`, `src/main.js` | даны готовыми. В `dom-app.js` добавлено только подключение debounce к полю поиска |

### HTTP-клиент

Основа перенесена из ПР5. Добавлены метод и тело запроса.

| Правило | Как сделано |
|---|---|
| Допустимые методы | `GET`, `POST`, `PATCH`, `DELETE`. Регистр приводится (`"patch"` → `PATCH`), `PUT` даёт `TypeError` |
| Тело | `JSON.stringify(body)` и `Content-Type: application/json`, только если тело передано |
| `GET` с телом | `TypeError` до отправки: такой запрос `fetch` всё равно отклонил бы |
| Порядок проверки ответа | `response.ok` → статус 204 → `Content-Type` → `response.json()` |
| Тайм-аут | 3000 мс по умолчанию, `AbortSignal.timeout` объединяется с внешним сигналом через `AbortSignal.any` |
| Вид отказа | определяется по сигналу: совпал `reason` тайм-аута → `timeout`, иначе сигнал прерван → `aborted`, иначе `network` |

Ответ 204 возвращается как `null` до чтения тела. Ошибка HTTP разбирается раньше
`Content-Type`, поэтому HTML от прокси с кодом 502 останется ошибкой `http`, а не станет
`invalid-response`.

### Доменный API

| Метод | Запрос | Что проверяется в ответе |
|---|---|---|
| `getTasks(filters, { signal })` | `GET /tasks?…` | массив задач без повторов id, `meta.total`, `meta.filters` |
| `getTaskById(id, { signal })` | `GET /tasks/:id` | `{ data: task }` |
| `getCategories({ signal })` | `GET /categories` | массив категорий |
| `loadInitialData(filters, { signal })` | оба запроса через `Promise.all` | как у двух методов выше |
| `createTask(draft, { signal })` | `POST /tasks` | созданная задача с серверным id |
| `updateTask(id, changes, { signal })` | `PATCH /tasks/:id` | изменённая задача |
| `setTaskCompleted(id, value, { signal })` | `PATCH /tasks/:id`, тело `{ completed }` | изменённая задача |
| `deleteTask(id, { signal })` | `DELETE /tasks/:id` | ровно `null`, то есть 204. Любое тело означает `invalid-response` |
| `resetDemoData({ signal })` | `POST /debug/reset` без тела | `{ reset: true, total }` |

Неизвестный фильтр, неверный тип или id ≤ 0 дают `TypeError` до сети. Последний аргумент
передаёт клиенту только `signal`: метод и тело задаёт сам доменный API, снаружи их не
подменить.

### Состояния интерфейса

```
            start / applyFilters / refresh / после мутации
                              │
                              ▼
                          loading ──── ответ устарел или aborted ──▶ (ничего)
                     ┌───────┼────────┐
               задачи есть  пусто   ошибка
                     ▼       ▼        ▼
                   ready   empty    error + «Повторить загрузку»
```

`empty` означает, что сервер ответил успешно и задач по условиям нет: счётчик равен 0.
`error` означает, что данных нет вовсе: список скрыт, видна кнопка повтора. Если категории
ещё ни разу не пришли, повтор снова вызывает `loadInitialData`, иначе только `getTasks`.

### Мутации

Все пять мутаций идут через внутреннюю `runMutation(operation, successMessage)`:

1. Если мутация уже идёт, повторный вызов игнорируется: двойной щелчок не создаст дубль.
2. `view.setMutationPending(true)` блокирует кнопки формы, сброса и карточек.
3. После успешного запроса выводится `notify(…, "success")` и список запрашивается заново
   с текущими фильтрами.
4. Ошибка выводится как `notify(messageForError(error), "error")`. При 404 список
   обновляется, а форма выходит из режима редактирования: запись удалили в другой вкладке.
5. В `finally` блокировка снимается в любом случае.

Редактирование отправляет только `title`, `priority` и `categoryId`, без `completed`.
Поэтому сервер сохраняет текущий статус задачи (сценарий 6).

### Защита от устаревшего ответа

Каждая загрузка делает две вещи:

- `state.loadController?.abort()`: предыдущий запрос рвётся, сервер не тратит на него
  время, а браузер показывает его как `canceled`;
- `seq = ++state.loadSeq`: после каждого `await` результат применяется, только если
  `seq === state.loadSeq`.

Одной отмены мало. Ответ мог уже прийти и стоять в очереди микрозадач, когда пользователь
сменил фильтр, и тогда `abort()` его не остановит. Номер загрузки отсекает и этот случай.
Ошибка `aborted` пользователю не показывается: её вызвал сам код, а новая загрузка уже
идёт. `destroy()` отменяет активную загрузку и запрещает любые изменения представления.

## Расширение: поиск с debounce

Поле «Поиск» само запускает фильтрацию через 400 мс после последнего нажатия. Под полем
есть подсказка, связанная через `aria-describedby`.

| Решение | Причина |
|---|---|
| Пауза 400 мс | в пределах 300–500 мс из задания. Короче — запрос на каждую букву, длиннее — ощутимая задержка |
| Debounce в `dom-app.js`, а не в контроллере | это свойство ввода. Контроллер остаётся синхронно проверяемым без таймеров |
| `cancel()` при отправке формы и «Сбросить фильтры» | иначе через 400 мс ушёл бы второй, лишний запрос |
| Отмена предыдущего запроса | уже есть в контроллере: debounce уменьшает число запросов, а `abort()` и номер загрузки защищают от гонки |

Проверка в браузере (сценарий Р протокола): слово «отчёт» набрано по букве с паузой 80 мс.
Во время ввода ушло **0** запросов, после паузы один `GET /tasks?q=отчёт`, на экране
задача № 31.

## Ответы на контрольные вопросы

1. **Почему `fetch` не отклоняет Promise при 404 и 500.** Для `fetch` это успешный
   обмен: сервер ответил, статус и тело получены. Отклонение означает, что ответа нет
   (сеть, CORS, отмена). Поэтому `response.ok` проверяет клиент, у нас это вид `http`.
2. **Порядок проверок.** `ok` → 204 → `Content-Type` → `json()`. Ошибка первой, потому
   что тело ошибки может быть HTML. 204 до `Content-Type`, потому что у пустого ответа
   нет ни тела, ни типа. JSON последним, так как его разбор поглощает поток тела.
3. **POST и PATCH.** `POST /tasks` создаёт новую запись, id назначает сервер. Повтор
   создаст вторую. `PATCH /tasks/:id` меняет переданные поля существующей записи, а
   остальные, например `completed` при редактировании, оставляет.
4. **201 и `Location`.** 201 сообщает, что ресурс создан, а не просто обработан.
   `Location: /api/tasks/35` даёт его постоянный адрес, по которому запись можно сразу
   прочитать.
5. **Почему у 204 не вызывается `json()`.** Тела нет, и `JSON.parse("")` бросит
   `SyntaxError`. Успешное удаление выглядело бы как `invalid-response`.
6. **CORS preflight и `no-cors`.** Приложение (5506) и API (5505) — разные источники.
   `PATCH`, `DELETE` и `Content-Type: application/json` не относятся к «простым»
   запросам, поэтому браузер сначала шлёт `OPTIONS`. `no-cors` разрешает только простые
   запросы и делает ответ непрозрачным: ни статуса, ни тела. Работать с API так нельзя.
7. **`empty` и `error`.** `empty` — успешный ответ с пустым массивом: данные актуальны,
   счётчик 0, подсказка сменить фильтр. `error` — данных нет: список скрыт, нужен повтор.
   Если их спутать, пользователь решит, что задач нет, хотя сервер просто недоступен.
8. **Почему `localStorage` больше не источник.** Источник истины — сервер. Локальная
   копия расходится с ним при работе из двух вкладок или устройств, после сброса и
   при серверной проверке. Браузерная проверка «не использует localStorage» это фиксирует.
9. **Зачем GET после мутации.** Сервер мог изменить данные иначе, чем ожидает клиент:
   назначить id, нормализовать поля, отфильтровать запись. Пример: в варианте 1
   выполненная задача обязана исчезнуть из выборки.
10. **Гонка при смене фильтра.** Запрос А (high) ушёл раньше, чем Б (low), но ответ А
    пришёл позже. Без защиты на экране окажется список high при выбранном low.
11. **Почему одного `AbortController` мало.** `abort()` не отменяет ответ, который уже
    разрешился и ждёт продолжения после `await`. Номер загрузки проверяется после
    каждого `await` и отсекает такой результат.
12. **Почему отмена — не ошибка.** Её вызвал сам код ради новой загрузки, и данные сейчас
    придут. Сообщение «ошибка» было бы ложным и мигало бы при каждом быстром фильтре.
13. **Клиент и сервер.** Клиент проверяет форму ради быстрой подсказки без запроса, а
    ответы — ради защиты интерфейса от чужого формата. Сервер обязан проверить всё заново
    (`VALIDATION_ERROR` 400): запрос можно отправить в обход формы, например через curl.
14. **Зачем `view` параметром.** Контроллер не зависит от DOM. В проверках ему
    подставляется объект-заглушка, записывающий вызовы, и сценарии с гонками проверяются в
    Node за миллисекунды.
15. **Почему `textContent`.** Название задачи приходит от сервера, а туда его мог записать
    кто угодно. `innerHTML` превратил бы `<img src=x onerror=…>` в исполняемую разметку.
    `textContent` всегда создаёт текст: браузерная проверка карточки это подтверждает.

## Вывод

Интерфейс задач работает поверх HTTP API: все операции идут через сервер, после мутации
список перечитывается, ответы проверяются по схеме. Самым тонким местом оказалась гонка
загрузок. Отмена через `AbortController` экономит сеть, но корректность даёт только номер
загрузки, проверяемый после каждого `await`. Разделение на клиент, доменный API,
контроллер и представление позволило проверить контроллер в Node без браузера (33 + 11
проверок). Браузер подтвердил то же на реальном сервере (14 проверок и 10 ручных
сценариев). Найдена и исправлена ошибка в одной учебной браузерной проверке, которая не
дождалась бы ответа ни при какой реализации.
