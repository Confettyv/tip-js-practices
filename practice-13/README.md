## Изоляция и тестовые двойники

- **fake store** (`tests/support/fake-store.js`) — рабочая реализация в памяти
  на 3 задачах. Отвечает так же, как настоящий store, но без SQL. Нужен для
  проверки маршрутов, парсера и обработчика ошибок. Отдельные методы
  подменяются в тесте: метод бросает ошибку с SQLSTATE; `updateTask` удаляет
  строку перед записью, моделируя гонку.
- **scripted pool** (`tests/unit/store.test.js`) — не база, а сценарий: пишет
  каждый вызов `{text, values}` и выдаёт заранее заданные `rows`/`rowCount` или
  ошибку. Тест ROLLBACK использует свой client: падает третья команда, проверяются
  точная последовательность `BEGIN → DELETE → DELETE → ROLLBACK`, один
  `connect()`, один `release()` и проброс того же объекта ошибки. `pool.query`
  в этом тесте вызывает `assert.fail`: обход client через пул тоже ловится.
- **HTTP helper** — `app.listen(0)`: порт назначает ОС, конфликтов с 5505 и
  соседними процессами нет. Сервер закрывается в `finally` (`withApi`) даже при
  упавшем assert.
- DB-тест закрывает pool во вложенном `finally` после повторного reset.

## Индивидуальный вариант

**Риск.** `API_PORT` принимает неоднозначную запись числа: ведущий ноль, пробелы,
знак или хвост. Конфигурация должна отклонять всё, кроме одной канонической записи.

**Тест** `вариант 1: readConfig отклоняет API_PORT с ведущим нулём, пробелами и хвостом`,
таблица случаев: `01`, `05505`, ` 5505`, `5505 `, `5505`, `5505abc`, `+5505`, `0x15B3`.

**Red на исходном коде.** `Missing expected exception: "05505"`. Регулярное
выражение ПР12 `/^\d+$/` пропускало ведущий ноль, а `Number('05505')` даёт 5505.
Парсер id в том же проекте (`parsePositiveId`) такую запись уже запрещал.

**Исправление** (`src/config.js:3`): `/^\d+$/` → `/^[1-9]\d*$/`. Green: тест
проходит, остальные 42 тоже.

**Контрольные мутации** (локально, не закоммичены, файл восстановлен и сверен `cmp`):

| Мутация                 | Строка                                          | Какие значения стали приниматься                      | Тест                                        |
| ----------------------- | ----------------------------------------------- | ----------------------------------------------------- | ------------------------------------------- |
| A: регулярка без якорей | `if (!/\d+/.test(raw))`                         | `05505`, ` 5505`, `5505 `, `5505`, `+5505`, `0x15B3`  | fail: `Missing expected exception: "05505"` |
| B: `parseInt`           | `Number.parseInt(raw, 10)` в проверке и разборе | `05505`, ` 5505`, `5505 `, `5505`, `5505abc`, `+5505` | fail: `Missing expected exception: "05505"` |
| восстановлено           | `/^[1-9]\d*$/`                                  | ничего                                                | pass                                        |

Таблица из восьми случаев нужна потому, что мутации ломают разные случаи.
`0x15B3` ловит только мутацию A, `5505abc` — только B.

## Исправленный дефект

Симптом: `API_PORT=05505` запускал сервер на 5505, хотя такая запись числа
неоднозначна (в части инструментов это восьмеричная форма), а для id API
отклоняет её. Воспроизводящий тест: тест варианта (red на `05505`). Причина:
регулярное выражение не запрещало ведущий ноль. Исправление: `/^[1-9]\d*$/`,
то же правило, что у `parsePositiveId`. Регрессией служит тот же тест,
устойчивость проверена двумя мутациями.

## Контрольные вопросы

1. Unit проверяет функцию или store без внешних процессов. HTTP integration проверяет всю цепочку Express через настоящий HTTP, но с fake store. DB integration проверяет SQL и драйвер на живой базе.
2. Каждый уровень ловит свой класс отказов. Повтор удорожает и замедляет набор, а ломается от одной правки во многих местах. Сценарий проверяется на самом дешёвом уровне, где риск виден.
3. Двойник заменяет зависимость в тесте. Fake — упрощённая рабочая реализация с состоянием. Scripted stub ничего не реализует: отдаёт заранее заданные ответы и записывает вызовы.
4. ОС выдаёт свободный порт: нет конфликта с запущенным API и параллельными тестами.
5. Иначе при упавшем assert останутся открытый сокет или соединения. Процесс тестов не завершится, следующий запуск упрётся в лимит пула.
6. Тест завершится раньше проверки: отказ пройдёт незамеченным или всплывёт в чужом тесте как unhandled rejection.
7. Он проверяет только то, что импорт существует. Поведение не вызывается и не сравнивается.
8. Когда много входов проверяют одно правило (границы, недопустимые значения). Значение передаётся в сообщение assert, чтобы был виден упавший случай.
9. Контракт — статус, код и поля. Редакторская правка текста ломает тест, хотя поведение не менялось.
10. Line — какие строки выполнились, function — какие функции вызывались, branch — какие ветви условий прошли (обе ли стороны `if`).
11. Покрытие говорит, что код выполнялся, а не что результат проверен. Плюс не покрываются отсутствующие проверки, как ведущий ноль в порте.
12. Скрытое исключение завышает процент. Явное и с причиной можно оценить на защите и пересмотреть.
13. Node считает todo запланированным тестом: даже его отказ не меняет код возврата.
14. Запускаются только отмеченные тесты (с `--test-only`) или поведение зависит от флагов. Остальной набор может тихо выпасть, а gate покажет зелёный.
15. HTTP-тест с фейком видит то, что видит клиент. Только так подтверждается, что обработчик не пропускает `message` драйвера, SQLSTATE и хост.
16. Это разные ветви: rollback, освобождение соединения в ошибке и проброс исходной причины в COMMIT-тесте не выполняются.
17. Нужны секрет, внешний процесс и изменение состояния. Быстрый gate должен работать на любой машине детерминированно и без базы.
18. Skip выглядит как успех: обязательная интеграция могла бы ни разу не выполниться, а отчёт был бы зелёным.
19. Prettier отвечает только за внешний вид кода. ESLint ищет ошибки и нарушения правил: неиспользуемые переменные, `==`, необработанные случаи.
20. Доказывает, что тест чувствителен к конкретной поломке. Не доказывает, что тест ловит другие поломки и что код верен в остальном.

## Ограничения набора

React-клиент и браузер не проверяются (это отдельный уровень e2e). Нет
нагрузочных проверок и одновременных запросов к реальной базе: гонка
смоделирована фейком. DB-тест восстанавливает данные в `finally`, но при
принудительном завершении процесса базу нужно проверить вручную.
