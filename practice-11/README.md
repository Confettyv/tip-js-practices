## Модель данных

**Сущности.** Категория (`id`, `name`) и задача (`id`, `title`, `completed`, `priority`, `category_id`). Связь «один ко многим»: у задачи ровно одна категория (`category_id NOT NULL` + внешний ключ), у категории от нуля до многих задач. Пустая категория допустима, задача без категории нет.

| Решение | Обоснование |
|---|---|
| `integer GENERATED BY DEFAULT AS IDENTITY` | id назначает база; режим `BY DEFAULT` позволяет загрузить прежние разреженные id ПР10 (1, 4, …, 34) |
| `CHECK (id > 0)` | в API id всегда положительный, 0 и отрицательные исключены и при явной вставке |
| `text` + `char_length BETWEEN 1 AND 100` | длина ограничена правилом, а не типом; `varchar(100)` не запретил бы пустую строку |
| `CHECK (value = btrim(value))` | строка с пробелами по краям **отклоняется**, а не обрезается: нормализует вход приложение |
| `NOT NULL` у всех обязательных полей | CHECK со значением NULL даёт «неизвестно» и не срабатывает, отсутствие запрещает только NOT NULL |
| `priority` с CHECK по списку, без DEFAULT | клиент обязан передать приоритет явно, как в API ПР10 |
| `completed boolean NOT NULL DEFAULT false` | новая задача по умолчанию в работе |
| `UNIQUE (name)` у категорий | название хранится один раз и однозначно определяет категорию |
| FK `ON DELETE RESTRICT` | категорию с задачами удалить нельзя: удаление не должно молча уничтожать задачи (как сделал бы CASCADE) |
| индекс `tasks_category_id_idx` | внешний ключ не создаёт индекс сам; он нужен выборкам по категории и проверке RESTRICT при удалении категории |

Ограничения названы явно (`tasks_title_trimmed`, `tasks_priority_allowed` и т. д.), чтобы по тексту ошибки было сразу видно, какое правило нарушено.

**API и SQL.** В базе `snake_case` (`category_id`), во внешнем JSON остаётся `categoryId`. Для выдачи в формате API используется алиас `category_id AS "categoryId"` (Q7), кавычки сохраняют регистр.

**Строки в SQL и JavaScript.** `char_length` считает символы, а `.length` в JavaScript считает единицы UTF-16, и для части emoji результаты разойдутся. `btrim` без аргумента убирает только обычный пробел, а `trim()` ещё табуляцию, переводы строк и неразрывный пробел. Поэтому проверки базы не заменяют валидацию API ПР10, а страхуют её.

## Исправленная ошибка

Во время работы ошибок не было, поэтому типичный сбой этапа воспроизведён намеренно в `tip_tasks_test`.

**Симптом.** Если после seed последовательность задач стоит в начальном состоянии, первая обычная вставка падает:

```
ERROR:  duplicate key value violates unique constraint "tasks_pkey"
DETAIL:  Key (id)=(1) already exists.
```

**Причина.** Seed вставляет явные id, а явная вставка в `BY DEFAULT` identity не вызывает `nextval`. Последовательность остаётся на 1 и выдаёт уже занятый id.

**Исправление.** В конце `02_seed.sql` для обеих таблиц вызывается `setval(..., max(id), true)`.

**Повторная проверка.** После `setval` по `max(id)` вставка без id в транзакции получила 35, затем ROLLBACK; в базе снова 12 задач.

## Контрольные вопросы

1. **Почему название категории хранится отдельно?** Чтобы оно было записано один раз. Переименование категории меняет одну строку, а не все задачи, и в разных задачах не появятся «Учёба» и «Учеба» как две разные категории.
2. **Какие строки допускает связь «один ко многим»?** В `tasks` у каждой строки ровно одна существующая категория. В `categories` строка может иметь любое число задач, включая ноль.
3. **Почему CHECK не заменяет NOT NULL?** Условие с NULL даёт NULL, а CHECK отклоняет только `false`. `char_length(NULL) BETWEEN 1 AND 100` пропустит NULL, поэтому отсутствие значения запрещается отдельно.
4. **Что защищает внешний ключ?** При INSERT и UPDATE задачи не даёт сослаться на несуществующую категорию. При DELETE и UPDATE id категории не даёт оставить задачи с висячей ссылкой: в нашем случае такая операция отклоняется.
5. **Почему RESTRICT, а не CASCADE?** CASCADE удалил бы все задачи категории одной командой, без предупреждения. Удаление пользовательских данных должно быть осознанным, поэтому сначала задачи переносят или удаляют явно.
6. **BY DEFAULT и ручные id.** База сама назначает id, если он не передан, и это безопасно при параллельных вставках. При этом явный id тоже разрешён, что нужно для переноса старого набора. Ручная нумерация всех строк требовала бы искать свободный id самому, и две вставки могли бы взять один и тот же.
7. **Зачем setval после seed?** Явные id не продвигают последовательность. Без `setval` она выдала бы 1, 2, … и столкнулась с уже загруженными строками.
8. **Почему после отката бывают пропуски?** `nextval` не транзакционен: выданное значение не возвращается при ROLLBACK, иначе параллельные транзакции пришлось бы ждать друг друга. Поэтому откаченная вставка оставляет дыру.
9. **LEFT JOIN и INNER JOIN.** INNER возвращает только пары с совпадением. LEFT возвращает все строки левой таблицы, а для строк без пары правые колонки заполняет NULL.
10. **Почему `count(t.id)`, а не `count(*)`?** Для пустой категории LEFT JOIN даёт одну строку с `t.id = NULL`. `count(*)` посчитает её как одну задачу, `count(t.id)` пропускает NULL и даёт 0.
11. **WHERE и HAVING.** WHERE отбирает строки до группировки и не видит агрегатов. HAVING отбирает уже сгруппированные строки по агрегатам, например `count(t.id) >= 4`.
12. **Для чего ORDER BY?** Без него порядок строк не гарантирован и может меняться после обновлений или смены плана. Отчёты и сравнение с ожидаемым результатом требуют стабильного порядка.
13. **`char_length`/`btrim` и JavaScript.** `char_length` считает символы, а JS `.length` единицы UTF-16, поэтому emoji из суррогатной пары JS посчитает за 2. `btrim()` убирает только обычный пробел, а JS `trim()` ещё табуляцию, переводы строк и неразрывный пробел. Поэтому API сохраняет свою проверку.
14. **Почему изменение файла схемы не обновляет базу?** Файл выполняется один раз при создании. База хранит результат, а не ссылку на скрипт, и учёта версий здесь нет. Для изменения существующей базы нужен отдельный скрипт `ALTER` (миграция).
15. **Почему данные PostgreSQL не видны в клиенте ПР10?** Клиент обращается к серверу ПР10, а тот хранит задачи в массиве в памяти и к базе не подключён. Подключение через драйвер `pg` будет в ПР12.
