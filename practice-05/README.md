### `buildUrl`

- `baseUrl` разбирается через `new URL`. Отклоняются: не строка, относительный адрес,
  схема кроме `http`/`https`, символ `?` или `#` в исходной строке.
- `path` очищается от краевых `/`. Запрещены пустые сегменты, `.` и `..`, схема в начале,
  `?` и `#`.
- Склейка: `url.pathname` без хвостовых `/` плюс `/` плюс путь. Поэтому `api/` и `/tasks`
  дают одну черту.
- Параметры собираются в новый `URLSearchParams`, входной объект только читается.
  Пропускаются `undefined`, `null` и `""`; `false` и `0` превращаются в строки
  `"false"` и `"0"`.

Пример: `q: "API & ошибки"` → `q=API+%26+%D0%BE%D1%88...`. Пробел, `&` и кириллицу
кодирует `URLSearchParams`, а не ручная замена.

### `requestJson`

```text
buildUrl → AbortSignal.timeout(ms) [+ внешний signal через AbortSignal.any]
   → try { await fetchFn(url, { GET, Accept, signal }) } catch → network | timeout | aborted
   → instanceof Response?        нет → invalid-response
   → response.ok?                нет → http (status, code, details из payload.error)
   → 204?                        да  → null
   → Content-Type JSON?          нет → invalid-response
   → response.json()             SyntaxError → invalid-response
```

Решения:

- **В `try` вокруг `fetch` больше ничего нет.** Любая ошибка обработки ответа
  (HTTP, формат) создаётся уже после него и не может превратиться в `network`.
- **Причину отказа определяет сигнал, а не текст ошибки.** `AbortSignal.any` хранит
  `reason` того сигнала, который сработал первым. Совпадает с `reason` тайм-аута — это
  `timeout`, иначе сигнал отменён — `aborted`, сигнал цел — `network`.
- **Тело HTTP-ошибки читается текстом и разбирается в `try`.** У 502 от прокси может
  быть HTML: тогда `code` равен `null`, а `kind: "http"` и статус сохраняются,
  сообщение — «HTTP 502: сервер вернул ошибку.».
- **JSON — это `application/json` и любой `*+json`**, параметр `charset` отбрасывается.
- **Ошибка чтения тела, не являющаяся `SyntaxError`, классифицируется как отказ `fetch`.**
  Тайм-аут может сработать, когда заголовки уже получены, а тело ещё идёт.
- **Конфигурация проверяется в фабрике.** `timeoutMs` — положительное безопасное целое
  (и в фабрике, и в вызове). `fetchFn` — функция. `signal` — `AbortSignal` или ничего.
  Иначе `TypeError` до запроса.

### Ошибки клиента

| `kind` | Когда | Пример из прогонов | Поля |
|---|---|---|---|
| `http` | статус вне 2xx | `/tasks/999` → 404 `TASK_NOT_FOUND`; `/debug/error` → 503 | `status`, `code`, `details`, `url` |
| `network` | ответ не получен | API остановлен: `cause` — `TypeError: fetch failed`, внутри `ECONNREFUSED` | `cause`, `url` |
| `invalid-response` | не `Response`, не JSON, битый JSON, неверная схема | `/debug/text`, `/debug/invalid-json` (`cause` — `SyntaxError`) | `cause`, `url` |
| `timeout` | истёк `timeoutMs` | 20 мс при ответе 150 мс, отказ через 24 мс, `cause` — `TimeoutError` | `cause`, `url` |
| `aborted` | вызывающий отменил | `controller.abort()` сразу после старта, `cause` — `AbortError` | `cause`, `url` |

Неверные аргументы (фильтры, `id`, конфигурация) — это ошибка программиста, а не
ответа. Для них `TypeError`, запрос не отправляется.

### `task-api.js`

- **Фильтры.** Обычный объект, только четыре ключа; `undefined` пропускается.
  `completed` — строго `boolean`, `priority` — из трёх значений, `categoryId` —
  положительное целое (`"2"` не принимается). `q` — строка, после `trim` не длиннее
  100. Результат — новый объект с исходными типами, в строку значения превращает
  `URLSearchParams`.
- **Коллекции.** Одна функция `readCollection` для задач и категорий: `data` — массив,
  каждый элемент проходит `isTask`/`isCategory`, id без повторов,
  `meta.total === data.length`. У задач дополнительно `meta.filters` должен быть
  объектом. Сообщение называет индекс плохого элемента.
- **Одна задача.** `id` проверяется до запроса, путь `/tasks/${id}`, ответ — `{ data: task }`.
- **`loadInitialData`.** Фильтры проверяются один раз до запуска. Неверный фильтр не
  отправит даже запрос категорий (свой случай С9). Затем
  `Promise.all([requestTasks(query), getCategories()])`: оба `requestJson` вызываются
  синхронно, до общего `await`. Отказ любого отклоняет результат той же ошибкой.
  `Promise.all` не отменяет второй запрос, он просто завершится впустую.

## Расширение А. Частичный результат

`loadInitialDataSettled(filters)` не заменяет `loadInitialData`, а живёт рядом. Его
Promise никогда не отклоняется из-за запроса (только из-за неверных фильтров, до
отправки).

```js
{ tasks: task[] | null, meta: object | null, categories: category[] | null,
  errors: { tasks?: Failure, categories?: Failure } }
// Failure = { kind, status, code, message }
```

Правила: часть, которая не пришла, равна `null`, а её причина лежит в `errors` под тем же
именем. Пустой `errors` означает полный успех. `ApiError` описывается своими полями,
любое другое исключение — `kind: "unexpected"`. Ошибка схемы тоже идёт в `errors`, потому
что проверка выполняется внутри каждого из двух Promise.

| Проверка | Отказ | Факт |
|---|---|---|
| А1 | нет | задачи `[4, 13, 16, 25, 34]` (`priority: "high"`), 3 категории, `errors = {}` |
| А2 | задачи: `http` 503 | `tasks` и `meta` — `null`, 3 категории, `errors.tasks` с `SERVICE_UNAVAILABLE` |
| А3 | категории: `network` | задачи `[1, 10, 16, 25, 31]`, `categories = null`, ключа `errors.tasks` нет |
| А4 | оба | все данные `null`, `errors` содержит `tasks` и `categories`, Promise выполнен |
| А5 | категория с пустым именем | 12 задач, `errors.categories.kind = "invalid-response"` |

Подмена отказов сделана обёрткой над настоящим клиентом: она отклоняет только
выбранный путь, остальные запросы идут к API.

## Вывод

`fetch` отклоняется только когда ответа нет совсем. 404 и 503 приходят как обычный
`Response`, поэтому клиент обязан сам проверять `ok`, тип содержимого и форму данных.
Чтобы ошибки не перепутались, `try` охватывает только `fetch`, а тайм-аут и отмена
различаются по сработавшему сигналу. Получение данных разделено на два слоя: транспорт
не знает о задачах, предметный модуль не знает о `fetch`. Из-за этого 26 проверок
проходят без сети, а интеграционные подтверждают, что те же модули работают с настоящим
сервером. Параллельная загрузка экономит ровно время более короткого запроса (614 → 305
мс), а `allSettled` позволяет показать половину данных, когда вторая половина недоступна.
