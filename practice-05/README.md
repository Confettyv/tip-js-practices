## Эксперимент с очередями выполнения

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | A, B, C, D, E, F | A, B, C синхронные. D и E микрозадачи, D поставлена в очередь раньше. F таймер, он после всех микрозадач |
| Фактический результат | A, B, C, D, E, F | Совпало с прогнозом |

- Синхронный код: A, B и C. B печатается сразу, потому что async-функция до первого `await` выполняется синхронно.
- Микрозадачи: D (обработчик `then`) и E (продолжение после `await null`). D попала в очередь первой, так как `then` вызван раньше `demonstrateAwait()`.
- Таймер с задержкой 0 попадает в очередь задач, а она обрабатывается только когда стек пуст и очередь микрозадач закончилась.
- Если удалить обработчик D, порядок остальных не изменится, просто E станет первой микрозадачей.

Потом добавил свой `Promise.resolve().then(...)` с меткой G после вызова `demonstrateAwait()`, но до C. Прогноз: A, B, C, D, E, G, F. Факт: `A, B, C, D, E, G, F`. G встала в очередь микрозадач после E, потому что продолжение после `await` было поставлено раньше, во время вызова `demonstrateAwait()`.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый учебный API, не менял |
| `src/api-client.js` | Транспорт: собрать URL, сделать GET, проверить статус и `Content-Type`, разобрать JSON, превратить любую ошибку в `ApiError` |
| `src/task-api.js` | Знает маршруты и схему задач: проверяет фильтры до запроса и данные после него |
| `src/variant.js` | Номер варианта и его фильтры |
| `src/main.js` | Консольный сценарий: загрузка, таблица, контрольная ошибка 404 |

`fetchFn` передаётся аргументом, чтобы в проверках подставить свою функцию и смоделировать 503, обрыв сети или зависший ответ без настоящего сервера. HTTP-ошибки проверяются отдельно от сетевых, потому что `fetch` для 404 и 503 не бросает исключение: ответ пришёл, но с плохим статусом. Если положить всё в один `try`, своя `ApiError` с `kind: "http"` попала бы в `catch` и превратилась бы в `network`. JSON после разбора всё равно проверяется, потому что `response.json()` гарантирует только правильный синтаксис, а не то, что у задачи есть `id` и `completed` логического типа.

## Последовательная и параллельная загрузка

Временный скрипт делал два запроса `/debug/delay?ms=300`: сначала двумя `await` подряд, потом через `Promise.all`. В работу этот скрипт не входит.

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 653 | 609 | 610 | Около суммы двух задержек |
| `Promise.all` | 306 | 305 | 305 | Около одной задержки |

Во втором случае оба запроса стартуют сразу и ждут сервер одновременно, поэтому общее время равно самому долгому запросу, а не сумме. Первый прогон чуть дольше из за установки соединения. В `loadInitialData` так же сделано через `Promise.all`, проверка 25 подтверждает, что оба запроса начинаются до общего ожидания.

## Отладка

Точки останова в `requestJson`: на вызове `fetchFn`, на строке после него, перед `response.json()` и в `catch` вокруг `fetchFn`.

Успешный запрос `getTasks({ completed: false, priority: "high" })`: URL `http://127.0.0.1:5505/api/tasks?completed=false&priority=high`, `response.status` 200, `response.ok` true, `Content-Type` `application/json; charset=utf-8`, payload `{ data: [3 задачи], meta: { total: 3, filters: ... } }`, ошибки нет.

Ошибочный запрос `getTaskById(999)`: URL `http://127.0.0.1:5505/api/tasks/999`, `response.status` 404, `response.ok` false, `Content-Type` тот же. До `response.json()` в успешной ветке не доходит, тело разбирается в `createHttpError`. Итог: `ApiError { kind: "http", status: 404, code: "TASK_NOT_FOUND", details: { id: 999 } }`.

## Вывод

Клиент получает задачи с учебного API, проверяет каждый ответ и все ошибки отдаёт как `ApiError` с понятным `kind`. Все наборы прошли: API 18, клиент 26, интеграция 13, свои 11.

Разница между случаями. Ожидание Promise это просто пауза, пока ответ не пришёл. HTTP-ошибка значит, что сервер ответил, но со статусом вне 2xx, и `fetch` при этом не бросает исключение. Сетевая ошибка значит, что ответа не было вообще. Неверный ответ это статус 200, но не JSON, битый JSON или данные не по схеме. Тайм-аут сработал, потому что истекло наше время, а явную отмену запросил вызывающий код через `AbortController`. Последние два выглядят одинаково на уровне `fetch` (оба отменяют сигнал), поэтому их различаю по тому, какой именно сигнал сработал.
