## Реализация

| Модуль | Обязанность |
|---|---|
| `task-validation.js` | `validateTaskInput(body, { partial, categoryIds })`: правила по полям, сбор всех ошибок в `details`, обрезка пробелов в `title` |
| `store.js` | `createTask`, `updateTask`, `deleteTask`, `reset`: данные в памяти, наружу отдаются копии |
| `write-routes.js` | маршруты записи: статус, заголовок `Location`, 404 при исчезнувшей записи |
| `json-body.js` | проверка `Content-Type`, разбор JSON до 16 КиБ, пустое тело → `INVALID_JSON` (готовый модуль) |
| `errors.js` | `ApiError` и общий обработчик, ошибки парсера переводятся в `INVALID_JSON` / `PAYLOAD_TOO_LARGE` (готовый модуль) |

**Проверка.** Для каждого поля своё правило: `title` строка 1–100 символов после `trim`, `priority` одно из `low/medium/high`, `categoryId` целое положительное из существующих категорий, `completed` строго `true`/`false`. Тело не объект (`null`, массив, строка) → `details.body`. Любой ключ вне списка, а также `id` и `completed` при создании, получают свою ошибку. При POST отсутствующие обязательные поля считаются ошибкой, при PATCH проверяются только переданные, но пустой объект запрещён.

**id.** Счётчик `nextId` стартует с максимума исходных id плюс один и только растёт. Удаление его не уменьшает, поэтому id удалённой записи никогда не достанется новой. Сброс возвращает счётчик к исходному значению.

**Непереданные поля.** `updateTask` собирает запись как `{ ...старая, ...changes, id }`: поля, которых нет в `changes`, остаются прежними, а `id` нельзя перезаписать.

**Без частичных изменений.** Валидация полностью завершается до обращения к хранилищу. Если хотя бы одно поле неверно, выбрасывается `ApiError` и `store` не вызывается вообще, поэтому верные поля из того же запроса тоже не применяются.

## Контракт

Ответы сняты `curl -i` с работающего сервера (служебные заголовки опущены):

```
POST /api/tasks  {"title":"Подготовить отчёт ПР10","priority":"high","categoryId":2}
HTTP/1.1 201 Created
Location: /api/tasks/35
{"data":{"id":35,"title":"Подготовить отчёт ПР10","completed":false,"priority":"high","categoryId":2}}

PATCH /api/tasks/35  {"completed":true}
HTTP/1.1 200 OK
{"data":{"id":35,"title":"Подготовить отчёт ПР10","completed":true,"priority":"high","categoryId":2}}

DELETE /api/tasks/35
HTTP/1.1 204 No Content
(тела нет)

PATCH /api/tasks/10  {"title":"","completed":"yes","owner":"me"}
HTTP/1.1 400 Bad Request
{"error":{"code":"VALIDATION_ERROR","message":"Данные не прошли проверку.","details":{
  "owner":"Неизвестное поле owner.","title":"Название обязательно.",
  "completed":"completed должен быть true или false."}}}

POST /api/tasks  {"title":
HTTP/1.1 400 Bad Request
{"error":{"code":"INVALID_JSON","message":"Некорректный JSON."}}
```

`INVALID_JSON` значит, что тело нельзя прочитать как JSON (синтаксис, пустое тело): до проверки полей дело не доходит. `VALIDATION_ERROR` значит, что JSON корректен, но значения не подходят под контракт. В этом случае `details` указывает каждое неверное поле.

Порядок проверок в PATCH: сначала id (`INVALID_ID` 400, `TASK_NOT_FOUND` 404), затем `Content-Type` (415) и разбор тела, затем поля. Поэтому `PATCH /api/tasks/999 {"bad":1}` отвечает 404, а не 400.

## Интеграция клиента

Клиент ПР8 обращается к `http://127.0.0.1:5505/api` (при протоколе использовался порт 18951 через `VITE_API_URL`). В журнале сети браузера все запросы `/api/tasks`, `/api/categories`, `/api/debug/reset` уходили на сервер ПР10, API ПР8 не запускался. **Изменения исходного кода клиента не потребовались**: контракт ответов (`{ data, meta }`, `{ error: { code, message, details } }`, 201/204/400/404) совпадает с учебным API.

При ошибке записи (сервер остановлен, 404 после удаления в другой вкладке) форма сохраняет черновик, показывает «Изменение не подтверждено: …» и разблокируется. Если запись прошла, а повторный GET упал, форма очищается с сообщением «Сохранено на сервере», а ошибка списка показывается отдельным баннером «Не удалось обновить список». Запись не повторяется, дубля нет.

## Исправленный дефект

**Симптом.** В пункте 11 ошибка выглядела бы как «Задача не найдена..»: сервер ПР10 отдаёт сообщения с точкой в конце, а клиент ПР8 после `message` добавлял вторую. При прогоне клиента с учебным API то же самое было видно на «Сеть недоступна..».

**Причина.** Шаблоны баннеров в `practice-08/src/App.jsx` вида `{message}. Показан…` рассчитывали на сообщения без финальной точки, а все тексты `ApiError` и обоих серверов заканчиваются точкой.

**Исправление.** Точка убрана из шаблонов, запасной текст `HTTP 503` в `api-client.js` получил свою. Правка вошла в коммит клиента `f15aff0`, сервер не менялся: тексты с точкой соответствуют контракту.

**Повторная проверка.** Весь протокол перепрогнан с API ПР8 и ПР10: в пунктах 9 и 11 одна точка, тесты клиента 52 / 0.

Отдельно проверены граничные запросы вне набора тестов: `__proto__` в теле, дробный и несуществующий `categoryId`, `completed: null`, тело `null` и строка, дубль ключа `title`, `id` в PATCH, id `007`, POST на `/tasks/10`, PATCH без `Content-Type`. Все получили ожидаемые 400/404/405/415, `title` из 100 символов с пробелами по краям принят после обрезки.

## Контрольные вопросы

1. **Почему проверка формы не заменяет серверную?** Форма относится к одному клиенту, и её легко обойти через `curl`, другой клиент или старую версию страницы. Сервер единственное место, через которое проходят все записи, поэтому только его проверка гарантирует корректность хранимых данных.
2. **Частичное обновление и замена.** PATCH меняет только переданные поля, остальные остаются. Замена (PUT) требует всю запись целиком, и непереданное поле было бы потеряно или стало бы ошибкой.
3. **Отсутствующий `completed` и `false`.** Проверяется наличие ключа (`Object.hasOwn(body, 'completed')`), а не истинность значения. Нет ключа значит «не менять», `false` значит «вернуть в работу».
4. **Строковый `categoryId` в query и в JSON.** В URL всё приходит строкой, у query других типов нет, поэтому сервер разбирает `"2"` в число. В JSON есть настоящие числа, и клиент обязан прислать `2`. Строка там означает ошибку на стороне клиента, молча её чинить не нужно.
5. **Когда увеличивать `nextId`.** Только после успешной проверки, в момент создания записи. Длина массива не годится: после удаления она уменьшается, и новый id совпал бы с уже выданным. Ссылки и кэши на старый id тогда указали бы на чужую запись.
6. **Перезагрузка браузера и перезапуск API.** После перезагрузки страницы данные на месте: клиент заново читает их с сервера. После перезапуска API всё созданное пропадает, потому что хранилище живёт в памяти процесса и стартует с исходного набора.
7. **Зачем 201 и `Location`.** 201 сообщает, что ресурс создан, а не просто «запрос выполнен». `Location` даёт адрес новой записи, его можно сразу запросить, не разбирая тело.
8. **Почему у DELETE 204 нет JSON.** 204 по определению ответ без тела. Клиент, увидев 204, не читает тело, а лишний JSON нарушил бы протокол и мог сломать разбор.
9. **`INVALID_JSON` и `VALIDATION_ERROR`.** Первое значит, что текст тела не является JSON и к полям дело не дошло. Второе значит, что JSON разобран, но значения нарушают правила, и `details` указывает каждое неверное поле.
10. **Как исключить частичное изменение.** Сначала проверить все поля и собрать ошибки, и только при пустом `details` вызывать хранилище. Одна ошибка отменяет весь запрос.
11. **Почему нельзя spread `req.body`.** В запись попали бы любые поля клиента: `id`, `owner`, `__proto__`, служебные флаги. В хранилище копируются только явно разрешённые и проверенные поля.
12. **Почему CORS не авторизация.** CORS говорит браузеру, каким страницам можно читать ответы. `curl` или серверный скрипт его не соблюдают, и запрос до сервера всё равно доходит. Кто имеет право на операцию, должен проверять сам сервер.
13. **Зачем снова проверять результат `updateTask`.** Между проверкой id и записью было асинхронное чтение тела, и за это время запись могла удалить другая операция. `null` из `updateTask` превращается в 404, а не в падение на `undefined`.
14. **Успешный POST и неуспешный GET.** Это две разные операции: запись уже выполнена на сервере. Если считать всё неудачей, пользователь нажмёт «Сохранить» ещё раз и получит дубль. Правильно сообщить об успехе записи и отдельно об ошибке обновления списка.
15. **Что проверяют тесты интеграции и что нужно в браузере.** Тесты гоняют HTTP-адаптеры клиента против настоящего сервера ПР10: пути, методы, статусы, форма ответов и ошибок. В браузере остаются CORS и журнал сети, `confirm`, задержка и двойное нажатие, вторая вкладка, остановка сервера, вывод небезопасного текста, сборка и preview.
