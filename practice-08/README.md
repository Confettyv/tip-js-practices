## Запуск

Из папки `practice-08`: `npm ci`.
Первый терминал: `npm run api`. Второй: `npm run dev`.
API: http://127.0.0.1:5505/api. Интерфейс: http://127.0.0.1:5173/.

При смене порта API указать адрес в `.env` по образцу `.env.example` и перезапустить Vite. Для сборки: `npm run build`, затем `npm run preview`; API остаётся запущенным.

## Полученный результат

Интерфейс «Доска задач» работает только через HTTP API: список, категории, создание, редактирование, смена статуса, удаление и восстановление учебного набора. Каждое изменение подтверждается сервером, после чего список запрашивается заново с текущими фильтрами. Локальная копия задач не правится оптимистично.

Экран разделён на две колонки (с 900 px): слева фильтры и форма, справа результат запроса. Над карточками сводка «в выборке / выполнено / в работе», строка состояния и баннеры ошибок. Карточка показывает номер, статус, приоритет (цветная полоса слева) и категорию.

Ограничение: сервер хранит данные в памяти процесса. После перезапуска `npm run api` или `POST /api/debug/reset` набор возвращается к 12 исходным задачам, а созданные записи пропадают. Это проверено сценарием 16.

## Архитектура

| Модуль | Ответственность |
|---|---|
| `api-client.js` | `fetch`, тайм-аут 3 с, разбор JSON, единый `ApiError` с полями `kind`, `status`, `code`, `details` |
| `task-api.js` | пути и методы API, проверка формы ответа (`isTask`, `isCategory`), `loadInitialData` берёт задачи и категории параллельно |
| `config.js` | один экземпляр api на модуль, адрес из `VITE_API_URL` |
| `hooks/useTaskData.js` | состояние загрузки, снимок данных, мутации, блокировка повтора |
| `App.jsx` | связывает хук, фильтры, форму и список; хранит `editingTask` и строку уведомления |
| `components/*` | только разметка и события, сетевых вызовов нет |

Эффект загрузки зависит от `api` и четырёх примитивов фильтра (`q`, `completed`, `priority`, `categoryId`), плюс `revision`. Объект `filters` в зависимости не попадает: новый объект с теми же значениями не должен вызывать лишний GET. `snapshot` тоже не входит, иначе каждый ответ запускал бы новый запрос.

В cleanup эффект сначала ставит `active = false`, затем вызывает `controller.abort()`. Служебные данные хранятся в ref: `mutationRef` (контроллер текущей записи и одновременно замок) и `mountedRef`. В state лежат только значения для отрисовки: `snapshot`, `status`, `error`, `mutationError`, `pending`, `revision`.

Отличие от ПР7: там данные жили в `localStorage` и изменялись синхронно. Здесь источник истины сервер, у каждой операции появилось ожидание, отмена и два вида ошибок, а после записи список перечитывается, а не правится на месте.

## Загрузка и изменения

**Старые ответы.** У каждого запуска эффекта свой `AbortController` и свой флаг `active`. При смене фильтра cleanup прошлого запуска отменяет запрос и запрещает запись результата. Флаг нужен, даже если реализация api проигнорирует `signal`. Проверка стоит и в `catch`, чтобы ошибка отменённого запроса не превратилась в баннер.

**Повторная мутация.** `mutate` записывает контроллер в `mutationRef` до первого `await`. Второй синхронный вызов видит занятый ref и сразу возвращает `false`. `pending` в state для этого не годится: оба вызова прочитали бы одно и то же старое значение. В `finally` ref освобождается только если там всё ещё своя операция.

**Ошибка POST и ошибка GET.** Успешная запись увеличивает `revision` и возвращает `true`, форма очищается, появляется «Сохранено на сервере». Если следующий GET упадёт, это отдельное состояние `status = 'error'` с баннером «Не удалось обновить список», запись при этом уже выполнена. Ошибка самой записи кладётся в `mutationError` («Изменение не подтверждено»).

**Черновик.** При ошибке записи `saveTask` возвращает `false`, `editingTask` и поля формы не сбрасываются, блокировка снимается. Снимок редактируемой задачи хранится в `App`, поэтому черновик не пропадает, даже если задача ушла из выборки по фильтру.

## Контрольные вопросы

1. **Зачем эффект, а не запрос в теле компонента?** Тело выполняется при каждой отрисовке и должно быть чистым. Запрос оттуда уходил бы при каждом рендере, а установка state по ответу запускала бы новый рендер и новый запрос. Эффект выполняется после отрисовки и только при изменении зависимостей.
2. **Когда вызывается cleanup?** Перед повторным запуском эффекта с новыми зависимостями и при размонтировании. В StrictMode при разработке ещё один раз сразу после первого монтирования.
3. **Почему callback не `async`?** Async-функция возвращает Promise, а React ждёт от эффекта функцию очистки или ничего. Поэтому внутри объявляется `load()`, и эффект вызывает её.
4. **Зависимости загрузки, почему нет `snapshot`?** `api`, `q`, `completed`, `priority`, `categoryId`, `revision`: всё, что меняет адрес запроса или требует перечитать данные. `snapshot` является результатом эффекта. В зависимостях он вызывал бы новый запрос после каждого ответа.
5. **Почему важна стабильная ссылка на api?** `api` входит в зависимости. Новый объект при каждом рендере перезапускал бы загрузку без конца. Поэтому он создаётся один раз в `config.js`.
6. **Зачем кроме AbortController проверять актуальность?** Ответ может прийти до вызова `abort`, но после смены фильтров, или реализация может не поддерживать `signal`. Флаг `active` гарантирует, что результат устаревшего запуска не попадёт в state.
7. **Почему защита нужна и в catch?** Отмена сама приходит как исключение `AbortError`. Без проверки каждая смена фильтра показывала бы баннер ошибки поверх свежего результата.
8. **Что проверяет дополнительный цикл StrictMode?** Что cleanup полностью отменяет работу setup: запросы отменяются, флаги сбрасываются, повторный setup восстанавливает их. Поэтому `mountedRef = true` ставится в setup, а не при объявлении.
9. **Почему одного pending в state мало?** Обновление state видно только в следующем рендере. Два click в одном такте читают одно и то же `pending === false`, и оба отправили бы POST. Ref меняется сразу, второй вызов видит замок.
10. **Что значит true при упавшем GET?** Запись подтверждена сервером: форму можно очищать. Упал только повторный показ списка, он отражается отдельной ошибкой, а повторять запись нельзя, иначе появится дубль.
11. **Почему нельзя автоматически повторять POST после тайм-аута?** POST не идемпотентен. Тайм-аут не говорит, дошёл ли запрос: сервер мог создать запись, и повтор создаст вторую.
12. **Почему смена фильтров не отменяет мутацию?** Фильтр относится к просмотру, запись к данным. Отмена ожидания не отменяет операцию на сервере, клиент просто перестал бы знать её итог. Новый GET после записи сам возьмёт актуальные фильтры.
13. **Что с операцией на сервере после отмены ожидания?** Обычно она выполняется до конца: `abort` закрывает ожидание ответа в браузере, а сервер уже мог принять и обработать запрос. Состояние нужно узнать новым GET.
14. **Чем `meta.total` отличается от общего числа?** `meta.total` равен числу задач, подходящих под текущие фильтры. Общее количество на сервере видно только запросом без фильтров.
15. **Что не проверяется в jsdom?** Реальная сеть и CORS, задержки и тайм-ауты, отмена `fetch` браузером, нативный `confirm`, остановка и перезапуск сервера, сборка Vite и preview, фактическая вёрстка. Поэтому эти сценарии пройдены в Chrome.
