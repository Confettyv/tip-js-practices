**Тема:** Создание собственного HTTP API

- ФИО: Мухамбетов Алим

- Вариант: 1 (`?completed=false`)

- Коммит сдаваемой версии: `cb3f35d` (реализация), отчёт добавлен следующим коммитом

## Цель и результат

Цель: написать на Express собственный API только для чтения, который отдаёт задачи и категории в формате, ожидаемом клиентом ПР8, строго проверяет входные данные и отвечает предсказуемыми JSON-ошибками.

Результат:

- работают маршруты `/api/health`, `/api/categories`, `/api/tasks`, `/api/tasks/:id`;
- список фильтруется по `completed`, `priority`, `categoryId` и `q`, фильтры объединяются через И;
- неизвестные, повторяющиеся и некорректные параметры дают 400 `INVALID_QUERY`;
- неверный id даёт 400 `INVALID_ID`, отсутствующая задача 404 `TASK_NOT_FOUND`;
- методы кроме GET, HEAD и OPTIONS получают 405 с заголовком `Allow`;
- автоматические проверки: 90 из 90, ручной протокол: 13 из 13.

## Установка и запуск

## Реализация

| Модуль | За что отвечает |
|---|---|
| `src/validation.js` | Превращает строки из URL в типизированные значения: `parsePositiveId` и `parseFilters`. Ничего не знает о задачах и HTTP, только бросает `ApiError` с кодом 400. |
| `src/task-service.js` | Чистые функции над массивом: `selectTasks` (фильтр) и `findTask` (поиск по id). Не знают о запросах и не меняют входной массив. |
| `src/store.js` | Хранит собственные копии исходных данных для каждого экземпляра приложения и вызывает функции сервиса. |
| `src/routes.js` | Связывает HTTP с остальными модулями: берёт параметры запроса, вызывает валидацию и хранилище, формирует `{ data, meta }`. |
| `src/app.js` | Фабрика приложения: общие заголовки и CORS, ответ 204 на OPTIONS, подключение роутера, 404 для неизвестных путей, обработчик ошибок. |
| `src/server.js` | Единственное место, где открывается порт. Проверяет номер порта и сообщает, если он занят. |

**Нормализация `false`.** Значение из URL всегда строка, а `Boolean('false') === true`. Поэтому `completed` сравнивается со строками `'true'` и `'false'` явно, а результат сравнения `raw === 'true'` уже настоящий boolean. Всё остальное (`0`, `1`, `True`, пустая строка) отклоняется с 400.

**Повторы и неизвестные параметры.** `req.query` для этого не подходит: повторяющийся ключ он превращает в массив, а при некоторых настройках разбирает вложенные конструкции. Маршрут строит `new URL(req.originalUrl, 'http://localhost').searchParams` и передаёт в `parseFilters`. Там сначала ищется имя вне списка `completed | priority | categoryId | q`, затем имя, которое встречается в `keys()` больше одного раза. Только после этого проверяются значения.

**Проверка id.** Строка целиком должна совпасть с `/^[1-9]\d*$/`: так отсекаются `4abc`, `04`, `-4`, `4.0`, `1e3` и пробелы. `Number('4abc')` или `parseInt('4abc')` здесь не подходят: первый даёт `NaN` без объяснения, второй молча вернёт 4. После перевода в число проверяется `Number.isSafeInteger`, иначе `9007199254740993` округлится до соседнего числа и найдётся не та запись. Тем же правилом проверяется `categoryId`.

**Порядок middleware.** Общие заголовки и OPTIONS → роутер `/api` (сначала GET-маршруты, затем `router.all` с 405 для тех же путей) → 404 `ROUTE_NOT_FOUND` → обработчик ошибок. GET-маршрут обслуживает и HEAD, поэтому до `router.all` доходят только POST, PUT, PATCH, DELETE и прочие. Если поставить `router.all` выше GET, любой GET получил бы 405.

## Контракт

| Метод и путь | Успех | Ошибки |
|---|---|---|
| `GET /api/health` | 200 `{ data: { status: 'ok' } }` | — |
| `GET /api/categories` | 200 `{ data: [...], meta: { total } }` | — |
| `GET /api/tasks?completed&priority&categoryId&q` | 200 `{ data: [...], meta: { total, filters } }` | 400 `INVALID_QUERY` |
| `GET /api/tasks/:id` | 200 `{ data: task }` | 400 `INVALID_ID`, 404 `TASK_NOT_FOUND` |
| Другие методы на этих путях | — | 405 `METHOD_NOT_ALLOWED`, `Allow: GET, HEAD, OPTIONS` |
| Неизвестный путь | — | 404 `ROUTE_NOT_FOUND` |

Успешный ответ (`GET /api/tasks/4`):

```json
{"data":{"id":4,"title":"Подготовить модель задач","completed":false,"priority":"high","categoryId":2}}
```

Ошибки:

```text
GET /api/tasks?completed=0   → 400 {"error":{"code":"INVALID_QUERY","message":"completed принимает только true или false.","details":{"param":"completed"}}}
GET /api/tasks/2             → 404 {"error":{"code":"TASK_NOT_FOUND","message":"Задача не найдена.","details":{"id":2}}}
POST /api/tasks              → 405 {"error":{"code":"METHOD_NOT_ALLOWED","message":"Метод POST не поддерживается для этого пути."}}, Allow: GET, HEAD, OPTIONS
```

`meta.total` — число задач **после** фильтрации, то есть длина `data`. `meta.filters` возвращает уже нормализованные значения (`false` boolean, а не строка), чтобы клиент видел, как сервер понял запрос.

**Граница с ПР10.** В ПР9 данные только читаются, хранятся в памяти и сбрасываются при перезапуске. Создание, изменение и удаление задач, разбор тела запроса и сохранение между запусками относятся к ПР10.

## Индивидуальный вариант

Вариант 1: `GET /api/tasks?completed=false`.

| Запрос | Ожидаемые статус и данные | Фактический результат |
|---|---|---|
| `http://127.0.0.1:18932/api/tasks?completed=false` | 200, id 4, 7, 13, 19, 22, 28, 34, `total` 7 | 200, `ids=[4,7,13,19,22,28,34]`, `meta={"total":7,"filters":{"completed":false,"priority":null,"categoryId":null,"q":""}}` |
| `http://127.0.0.1:18932/api/tasks?completed=0` | 400 `INVALID_QUERY` | 400, `{"error":{"code":"INVALID_QUERY","message":"completed принимает только true или false.","details":{"param":"completed"}}}` |
| `http://127.0.0.1:18932/api/tasks/7` (из выборки) | 200, задача 7, `completed: false` | 200, `{"data":{"id":7,"title":"Проверить методы массивов","completed":false,"priority":"low","categoryId":1}}` |
| `http://127.0.0.1:18932/api/tasks/2` | 404 `TASK_NOT_FOUND` | 404, `{"error":{"code":"TASK_NOT_FOUND","message":"Задача не найдена.","details":{"id":2}}}` |

Объяснение. `completed=false` превращается в boolean `false`, и остаются задачи, у которых `completed === false`: это все задачи, кроме 1, 10, 16, 25, 31. `completed=0` отклоняется, потому что в контракте нет приведения чисел к логическому типу: иначе пришлось бы решать, что значат `2` или `yes`. Id 2 синтаксически верен (проходит `parsePositiveId`), но такой записи нет, поэтому ответ 404, а не 400.

## Исправленный дефект

**Симптом.** После первой реализации HTTP-тесты прошли 52 из 52, а модульные 37 из 38. Упал тест «Логика работает с другим массивом, без жёстко заданных id»: `assert.equal(findTask(data, 101), data[0])` сообщал о неравенстве, хотя `actual` и `expected` в выводе выглядели одинаково.

**Причина.** `findTask` возвращал копию `{ ...task }`, чтобы клиент «не получил ссылку на хранилище». `assert.equal` в строгом режиме сравнивает объекты по ссылке, а копия — это другой объект. Копирование было лишним: исходные данные заморожены, хранилище и так работает со своими копиями, а `res.json` сериализует объект и ссылку наружу не передаёт.

**Исправление.** `findTask` возвращает найденный элемент (`tasks.find(...) ?? null`), `selectTasks` — результат `filter` без `map` с копированием.

**Повторная проверка.** `npm test`: 90 из 90; тест «Фильтрация и запрещённое удаление не изменяют исходный набор» тоже проходит, то есть отказ от копий мутаций не добавил.

## Контрольные вопросы

1. **Node.js и браузер.** Язык тот же, окружение разное. В браузере есть `window`, DOM, `fetch` с CORS и песочница без доступа к диску. В Node.js нет DOM, зато есть файловая система, процессы, сеть на уровне сокетов (`http`, `fs`, `process`) и модули из npm. Код сервера живёт долго и обслуживает много клиентов, поэтому ошибка в одном запросе не должна ронять процесс.
2. **Выбор маршрута.** Путь и HTTP-метод. Query на выбор обработчика не влияет: `/api/tasks?completed=false` и `/api/tasks` обрабатывает один и тот же маршрут, а параметры читаются уже внутри него.
3. **`req.params` и query.** `req.params` — именованные части самого пути (`:id` в `/tasks/:id`), они обязательны и определяют ресурс. Query — необязательные пары после `?`, они уточняют выборку (фильтр, поиск). Без `:id` маршрут не совпадёт, без query — совпадёт.
4. **Строка `'false'`.** Всё из URL приходит строкой, а любая непустая строка истинна: `if ('false')` выполнится. Без явного сравнения фильтр `completed=false` вернул бы выполненные задачи.
5. **Весь id и `isSafeInteger`.** `parseInt('4abc')` вернёт 4, и запрос к несуществующему ресурсу молча отдаст задачу 4. Числа больше `2^53 - 1` не представимы точно: `Number('9007199254740993')` даёт `...992`, то есть другой id. Полная проверка гарантирует, что найдено именно то, что запросили.
6. **200 и 404.** Список как ресурс существует; то, что под фильтр ничего не подошло, — нормальный ответ «ноль совпадений». Задача с конкретным id — отдельный ресурс, и если её нет, запрошенного ресурса не существует.
7. **`TASK_NOT_FOUND` и `ROUTE_NOT_FOUND`.** Первое: маршрут правильный, id корректный, но записи нет (ответ дал обработчик `/tasks/:id`). Второе: ни один маршрут не подошёл к пути вообще, например опечатка в URL. Клиенту это помогает отличить «данные удалены» от «ошибка в адресе».
8. **405 и 404.** 404 — по этому пути ничего нет. 405 — путь есть, но не поддерживает этот метод. `Allow` перечисляет допустимые методы, чтобы клиент понял, что можно сделать (по RFC 9110 заголовок в 405 обязателен).
9. **`meta.total` при фильтрах.** Число найденных задач после применения всех фильтров, а не размер всей коллекции. Сейчас совпадает с `data.length`; при пагинации в будущем стало бы полным числом совпадений.
10. **Порядок middleware.** Express вызывает их сверху вниз до первого ответа. CORS-заголовки стоят первыми, поэтому есть и в ошибках. 404 после роутера срабатывает, только если ни один маршрут не ответил. `router.all` после GET даёт 405 лишь непредусмотренным методам. Обработчик ошибок последний, чтобы ловить ошибки всех слоёв выше.
11. **Четыре параметра.** Express отличает обработчик ошибок от обычного middleware по `function.length === 4`. Если убрать неиспользуемый `next`, функция станет обычным middleware и ошибки до неё не дойдут.
12. **Фабрика отдельно от порта.** `createApp()` можно создать в тестах без занятия порта (или на порту 0), с подменённым хранилищем, много раз и с чистыми данными. `server.js` нужен только для реального запуска.
13. **Данные при внутренней ошибке.** Только общий код и нейтральный текст (`INTERNAL_ERROR`, «Внутренняя ошибка API.»). Стек, текст исключения, пути к файлам и SQL — в лог сервера, не клиенту: они раскрывают устройство системы.
14. **CORS не авторизация.** CORS — правило браузера: можно ли скрипту с чужого origin прочитать ответ. curl, Postman или другой сервер его игнорируют. Кто именно делает запрос и что ему разрешено, решают токены, сессии и проверки на сервере.
15. **Что нужно в ПР10.** Маршруты `POST /tasks`, `PATCH`/`PUT /tasks/:id`, `DELETE /tasks/:id` (и сброс, если клиенту он нужен); `express.json()` с проверкой тела и ответами 400/415; изменяемое хранилище; коды 201 и 204 с `Location`; расширение `Allow` и CORS (`POST, PATCH, DELETE`, заголовок `Content-Type`) на новые методы.
