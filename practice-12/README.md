Пул держит готовые соединения: запросу не нужно каждый раз проходить TCP и
аутентификацию, а число соединений ограничено сверху. Сервер открывает порт
только после `ping()`; при SIGINT/SIGTERM закрывает HTTP, затем `pool.end()`.

## SQL операций

| Операция | SQL | values (пример) |
|---|---|---|
| список | `SELECT … FROM public.tasks WHERE completed = $1 AND priority = $2 AND category_id = $3 AND title ILIKE $4 ESCAPE '\' ORDER BY id` | `[false, "high", 2, "%подгот%"]` |
| одна | `SELECT … WHERE id = $1` | `[4]` |
| создать | `INSERT INTO public.tasks (title, priority, category_id) VALUES ($1, $2, $3) RETURNING …` | `["Проверить PostgreSQL", "high", 2]` |
| изменить | `UPDATE public.tasks SET completed = $1 WHERE id = $2 RETURNING …` | `[true, 36]` |
| удалить | `DELETE FROM public.tasks WHERE id = $1` → `rowCount === 1` | `[36]` |

Условия и поля UPDATE собираются из фиксированных списков пар «ключ → колонка».
Порядок не зависит от порядка ключей в запросе, `false` не теряется
(`Object.hasOwn`, а не проверка на истинность). Пустой или неизвестный набор
полей отклоняется до базы. `completed` при создании назначает `DEFAULT false`.

**Поиск.** `escapeLikePattern` экранирует `\`, `%`, `_`, затем значение
оборачивается в `%…%`. **camelCase.** В выборке `category_id AS "categoryId"`:
без кавычек PostgreSQL привёл бы алиас к `categoryid`.

## Транзакция reset

Один `client` из `pool.connect()`: `BEGIN` → `DELETE tasks` → `DELETE categories`
→ вставка 3 категорий и 12 задач через `unnest($1::integer[], …)` (каждый столбец
одним массивом-параметром) → `setval` для обеих sequence → `COMMIT`. При ошибке
`ROLLBACK` (его собственная ошибка не скрывает исходную) и проброс, `release()`
в `finally` всегда. Задачи удаляются раньше категорий из-за FK `ON DELETE RESTRICT`.

## Исправленный дефект

Шаг 11 протокола: API ходил к базе через TCP-прокси, прокси останавливался. До
исправления `/api/health` и `/api/tasks` отвечали **500 INTERNAL_ERROR**.
Причина: при недоступном сервере ошибку создаёт не PostgreSQL, а Node
(`ECONNREFUSED`) или драйвер pg («timeout exceeded when trying to connect»,
«Connection terminated…»). SQLSTATE класса 08 у них нет, поэтому `errors.js` их
не узнавал. В `isConnectionFailure` добавлены сетевые errno-коды и сообщения
драйвера (у этих ошибок нет кода). Регрессия: `checks/database-unavailable.test.js`,
3 случая. До исправления 0/3, после 3/3; ручной шаг 11 теперь даёт 503.

## Ответы на контрольные вопросы

1. Соединение дорого открывать (TCP, аутентификация, процесс на сервере), а их число ограничено. Пул переиспользует готовые и не даёт открыть лишние.
2. `pool.query` берёт любое свободное соединение на одну команду. `client.query` выполняется на закреплённом соединении.
3. Транзакция принадлежит соединению: `BEGIN` на одном и `INSERT` на другом не связаны, откатывать будет нечего.
4. Соединение не вернётся в пул. После пяти утечек новые запросы ждут и падают по таймауту.
5. Параметр передаётся как значение отдельно от текста SQL. Имя колонки — часть текста, поэтому берётся только из фиксированного списка.
6. Один набор фильтров даёт один и тот же текст и номера параметров. Так запрос предсказуем, тестируем и не зависит от порядка ключей в JSON.
7. В LIKE `%` — любая строка, `_` — любой символ, `\` — экранирование. Без обработки поиск «50%» нашёл бы лишнее.
8. Идентификатор без кавычек приводится к нижнему регистру, получилось бы `categoryid`.
9. `max(id)+1` при двух одновременных POST даёт один id и конфликт, а удалённый id выдаётся повторно. Sequence атомарна.
10. Пустой результат означает, что запрос прошёл и строки нет (404). Ошибка запроса — это сбой (400/503/500).
11. Вернуть строку в том виде, как её сохранила база (id, DEFAULT), без второго SELECT и без гонки между ними.
12. Между GET и UPDATE строку может удалить другой запрос. Поэтому `RETURNING` пуст, и API отвечает 404.
13. Проверка в JS и запись — два шага; категорию могут удалить между ними. FK проверяет в момент записи и для любого клиента базы.
14. Код стабилен и задокументирован. Текст зависит от версии, локали и формулировки.
15. Текст PostgreSQL, SQL, имена таблиц и ограничений, хост, порт, роль, стек.
16. После обновления страницы данные мог держать и процесс API в памяти. Перезапуск API доказывает, что они в базе.
17. Любой посетитель сотрёт все данные одним POST.
18. ROLLBACK отменяет изменения строк транзакции. `nextval` не откатывается: выданные номера пропадут, поэтому id идут с дырами. Сам reset сдвигает sequence на 34 через `setval`, поэтому после reset id снова начинаются с 35.
19. Без `DATABASE_URL` DB-тест пропускается. Остальные работают с поддельным хранилищем и проверяют только контракт.
20. Колонка `owner_id` и FK, условие `owner_id = $n` в каждом запросе и в UPDATE/DELETE, middleware аутентификации, закрытие reset, проверка прав и 403/404 на чужие записи.

## Вывод

PostgreSQL сделал данные постоянными, а целостность обеспечивает сама база
(FK, CHECK, DEFAULT, identity). Самым полезным шагом оказалась проверка падения
базы: тесты по SQLSTATE проходили, но при реальном отказе соединения API
отвечал 500. Ошибки подключения приходят не от PostgreSQL и требуют отдельной
обработки.
